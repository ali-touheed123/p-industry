## 6. SECURITY DEFINER Safety Review

Both deployed functions run with `SECURITY DEFINER` privileges under PostgreSQL owner `postgres`. An independent security analysis evaluated the attack surface:

### 6.1 `search_path` Hijacking Analysis
- **Configured Setting:** `SET search_path = public, pg_temp`
- **Evaluation:**
  - `public` is listed first. Queries referencing unqualified table names (`vouchers`, `token_transactions`, `suppliers`) resolve to `public` schema tables before `pg_temp`.
  - While modern hardening standards often recommend `search_path = ''` with fully schema-qualified names (`public.vouchers`), the current setting prevents untrusted schemas from prepending themselves.
  - Furthermore, `pg_temp` exploitation requires an active SQL session capable of creating objects in the temporary schema. Because `EXECUTE` privileges are revoked from `PUBLIC`, `anon`, and `authenticated`, untrusted actors cannot invoke these routines directly.

### 6.2 Dynamic SQL & Injection
- **Audit:** Neither `create_voucher_atomic` nor `create_purchase_atomic` uses `EXECUTE format(...)` or string concatenation in SQL queries.
- **Result:** **Zero dynamic SQL injection surface.**

### 6.3 Row-Level Security (RLS) Bypass & Tenant Boundaries
- **Evaluation:** Because `SECURITY DEFINER` executes under `postgres` (superuser / table owner), PostgreSQL bypasses Row-Level Security policies.
- **Mitigation:** The functions cannot rely on RLS and must enforce tenant boundaries explicitly in application logic:
  - In `create_voucher_atomic`:
    - `WHERE t.id = ANY(cp_token_ids) AND t.tenant_id = p_tenant_id`
    - `WHERE id = v_party_id AND tenant_id = p_tenant_id`
    - `cardinality(v_locked_rows) <> jsonb_array_length(p_token_allocations)` fail-closed guard.
  - In `create_purchase_atomic`:
    - `WHERE id = ANY(p_token_ids) AND tenant_id = p_tenant_id`
    - `WHERE id = v_supplier_id AND tenant_id = p_tenant_id`
    - `v_token_count <> array_length(p_token_ids, 1)` fail-closed guard.
- **Result:** **`VERIFIED`**. Tenant isolation is rigorously maintained through parameterized SQL filters.

### 6.4 Routine Privileges in Production Catalog
Inspection of `information_schema.routine_privileges` in production confirms:
- `create_voucher_atomic`: `postgres` (owner) + `service_role` only.
- `create_purchase_atomic`: `postgres` (owner) + `service_role` only.
- `PUBLIC`, `anon`, `authenticated`: **REVOKED (No privileges).**
- Supabase security lints: `0` advisories.

## 8. Idempotency and Concurrency Assessment

The Gate 9 report discussed idempotency. This audit distinguishes between five distinct operational scenarios:

| Failure / Concurrency Scenario | Protection Mechanism | Tested in Harness? | Actual System Behavior |
|---|---|:---:|---|
| **Duplicate Token IDs in Request** | Set cardinality check | ✅ Yes (Cases 10, 11) | Rejects with `Duplicate token IDs supplied` before writing. |
| **Concurrent Race for Same Tokens** | `ORDER BY id ASC FOR UPDATE` | ✅ Yes (Cases 26, 27, 28) | First session commits; second session blocks and fails with `Token not available` or `Requested quantity exceeds available`. |
| **Immediate Replay of Completed Payload** | Token `usage_status` guard | ✅ Yes (Case 30) | Replay is rejected because tokens are marked `'used'`. Zero double-spend. |
| **Client Retry After Network Timeout (Voucher)** | Token status guard | ⚠️ Partially | Tokens are already `'used'`. The retry is rejected with an error. No double voucher is created, but client receives an error rather than original voucher receipt. |
| **Client Retry After Network Timeout (Purchase)** | `uq_purchases_tenant_purchase_no` | ⚠️ Statically Verified | Unique constraint blocks duplicate purchase insertion (`23505`). UI catches this error and informs the user. |
| **Network Drop After Commit (Idempotency Cache)** | None | ❌ Not Implemented | System has **no dedicated idempotency key table** to replay cached successful HTTP responses after client disconnects. |

**Audit Finding:** The system guarantees **strict double-spend protection and duplicate-entry prevention**, but does **not provide transparent HTTP response replay** (RFC 7240 / Idempotency-Key pattern). This distinction is critical for payment operations.

## 10. Migration-History Assessment

### 10.1 The Discrepancy
- **Local repository files:**
  - `supabase/migrations/20261013_03_fix_create_voucher_atomic.sql`
  - `supabase/migrations/20261013_04_fix_create_purchase_atomic_valuation.sql`
- **Production `schema_migrations` table:**
  - `version: 20261014140400, name: 20261013_03_fix_create_voucher_atomic`
  - `version: 20261014142617, name: 20261013_04_fix_create_purchase_atomic_valuation`

### 10.2 Operational Collision Risk
1. **Supabase CLI Behavior:**
   - The Supabase CLI orders migrations by their numeric/timestamp prefix.
   - The prefix `20261013` (8 digits) is lexicographically and numerically smaller than `20261013001803` (14 digits).
   - If a developer executes `npx supabase db push` locally against production:
     - The CLI will perceive `20261013_03` as an "unapplied historical migration" older than the ledger HEAD.
     - Depending on the CLI version, it will either **halt with an out-of-order migration error** or attempt to **re-execute the script**.
2. **Mitigation Recommendation:**
   - Either:
     a) Rename local files to match the production ledger timestamps:
        - `20261014140400_fix_create_voucher_atomic.sql`
        - `20261014142617_fix_create_purchase_atomic_valuation.sql`
     b) OR maintain the documented policy that production deployments bypass `supabase db push` and utilize the Supabase Management API (`apply_migration`).
